# SG64 profile (N64 Engine)

Shiny Gen is an AI game maker: describe a game and the AI builds it, on web, iOS and Android.

> Part of the [Shiny Gen game languages](README.md). Canonical site: **<https://shinygen.ai>**

The N64 Engine is a 3D engine written for Shiny Gen, including its own RSP microcode. Its language
profile is called **sg64**. The game is one source file, `main.sg64`, compiled to MIPS machine code and
linked into a real cartridge image (a ROM you can download). Unlike the two 2D profiles, this machine
draws **triangles**: there are no sprites and no tile hardware.

## The machine

| | |
|---|---|
| screen | 320x240, the only mode |
| CPU | 93.75 MHz, 32-bit code, with a floating-point unit |
| memory | 4 MiB of RAM (8 MiB with the memory expansion, which the compiler requests on its own for a very large game) |
| frame | about 3,125,000 cycles at 30 Hz; 60 Hz halves it, 20 Hz gives 4,687,500 |
| entry point | one `void main(void)`, with a frame loop you write |
| stack | 128 KiB |
| cartridge | up to 64 MiB; assets are stored in it and read when needed |
| save | a typed, versioned, checksummed block: 508 words, or 8,188 on the larger chip |
| types | `int`, `s32`, `u32` are 32 bits; `fx` is 16.16; `f32` is an IEEE single |

## The budget that matters: triangles

A frame is spent on vertices, not on your code.

- **The measured budget is about 2,970 triangles at 30 Hz**, before the fill cost of the drawing
  hardware, which only takes the number down. Textured low-poly pixel meshes measured about 1,500 to
  1,700 triangles a frame.
- **Budget the scene before you build a model:** triangles per model times copies on screen, plus
  everything else. Keep the total under about 2,500 at 30 Hz. Nine fish of 392 triangles is already
  3,528 on their own. A creature seen many times wants roughly 80 to 150 triangles and gets its look
  from silhouette, colour and texture. Spend triangles on the one hero model.
- A mesh of N triangles with V vertices in B batches costs about `V x 534 + N x 150` cycles, plus 600
  for each triangle actually on screen, plus `2 x B x 490` for microcode overlay swaps, plus 4,700 for
  each texture it binds.
- Cheap things: a forty-glyph text line, a billboard, a whole display list. Vertices are the scarce
  quantity.
- `frame_cost(&c)` writes the frame's verdict and `frame_over_budget()` is the one-word answer.

Over budget is flagged, never slowed. The app keeps running at full speed and tells you after a build
and again at export. On a real console the same cartridge would run slower.

## How a game runs

```c
#define SPEED  8.0fx

u32 duck;                       /* a handle is a u32, and 0 means "it failed" */
sg64_vec3 pos;
fx model[16];                   /* a matrix is sixteen fx, and it is yours */

void main(void)
{
    sg64_dl dl;                 /* the display-list writer lives on your stack */
    sg64_vec3 v;

    sys_init(30);               /* 30 Hz. Once, first. */
    duck = mesh_load(MESH_duck);
    cam_perspective(0.1666fx, 32.0fx, 2048.0fx);   /* field of view in TURNS: 60 degrees */
    v = vec_make(0.5fx, 0.7fx, 0.5fx);
    light_dir(v, 0xFFF2D0FFu);
    light_ambient(0x505868FFu);
    pos = vec_make(0.0fx, 0.0fx, 0.0fx);

    for (;;) {
        frame_begin(&dl, 0x203040FFu);      /* waits, clears, polls the pad */

        pos.x = pos.x + pad_stick_x() * SPEED;
        pos.z = pos.z - pad_stick_y() * SPEED;

        v = vec_make(0.0fx, 200.0fx, 800.0fx);
        cam_look(v, pos);
        mat_translate(model, pos);
        mesh_draw(duck, model);

        text_print(8, 8, "hello");          /* x, y in pixels, then the string */

        frame_end(&dl);                     /* finishes, kicks, waits, swaps */
    }
}
```

- Call `sys_init(30)` first, once. It takes the frame's memory and chooses the frame rate.
- `frame_begin(&dl, clear_rgba)` waits for the video field, starts the list, clears colour and depth,
  and polls the controller. Do not poll the pad again inside a frame.
- `frame_end(&dl)` finishes the list, draws, waits and swaps the buffers.
- Returning from `main` is a panic.
- A baked 3D model is centered and quantized so its widest half is 256 units, so a model is about 512
  units across at the identity matrix. Scale with the matrix you give `mesh_draw`.

A game that needs no 3D model files at all is in
[examples/coin-field-n64](../../examples/coin-field-n64/README.md).

## Fixed point, `f32` and angles

- `fx` is 16.16, reaching about -32768 to 32767.9999. A literal's raw value here is 256 times what it
  is on the 2D profiles.
- **Angles are turns.** `1.0fx` is a full circle and `0.25fx` is a right angle, so wrapping an angle is
  a mask rather than a modulo. `fx_sin`, `fx_cos`, `fx_tan`, `fx_atan2`, `fx_asin` and `fx_sqrt` are
  table driven, so the app and the hardware produce the same bits.
- `f32` literals end in `f` (`1.5f`). It has `+ - * /`, the comparisons, `f32_sqrt` and `f32_abs`.
  There is no `double`, no libm, and no implicit conversion: use `f32_from_int`, `f32_to_int` (which
  truncates), `f32_from_fx` and `f32_to_fx`. A bare `0.5` is an error; write `0.5f` or `0.5fx`.
- The engine's own functions take and return `fx`, never `f32`.
- Nothing forms an `fx` square: `fx * fx` overflows once either side passes 181. Use `vec_len` and
  `vec_dist`, which compute in 64 bits, or compare a length against a budget.

## Engine functions

Names are short and prefixed by what they do. There are two tiers, and you want the upper one: the
engine tier (`frame_`, `cam_`, `mesh_`, `anim_`, `text_`, `hud_`, `col_`, `pad_`, `save_`) holds the
state for you. The `dl_` tier writes display lists by hand.

| Group | Main calls |
|---|---|
| System | `sys_init(hz)`, `sys_hz`, `sys_mem_free`, `sys_mem_mark`, `sys_mem_release`, `sys_print` |
| Frame | `frame_begin(&dl, clear_rgba)`, `frame_end(&dl)`, `frame_count`, `frame_time`, `frame_tris`, `frame_cost`, `frame_over_budget` |
| Camera | `cam_perspective(fov_turns, near, far)`, `cam_ortho`, `cam_look(eye, at)`, `cam_look_up`. One camera per frame |
| Light and fog | `light_dir(dir, rgba)`, `light_ambient(rgba)`, `light_off`, `fog_on(near, far, rgba)`, `fog_off` |
| Vectors | `vec_make`, `vec_add`, `vec_sub`, `vec_scale`, `vec_dot`, `vec_cross`, `vec_len`, `vec_dist`, `vec_norm`, `vec_lerp` |
| Matrices | `mat_identity`, `mat_mul`, `mat_translate`, `mat_scale`, `mat_rot_x`, `mat_rot_y`, `mat_rot_z`, `mat_rot_axis`, `mat_trs`, `mat_apply`, `mat_lookat` |
| Models | `mesh_load(MESH_x)`, `mesh_draw(handle, matrix)`, `mesh_draw_part`, `mesh_mode`, `mesh_tris`, `mesh_size` |
| Textures | `tex_load(TEX_x)`, `tex_bind`, `tex_wrap` |
| Animation | `anim_load(CLIP_x)`, `anim_play(mesh, clip, seconds, loop)`, `anim_frame`, `anim_rest`; skeletons with `skel_load`, `skel_pose` |
| Billboards | `bill_draw(position, w, h, color)` |
| HUD and text | `hud_rect`, `hud_sprite`, `hud_frame`, `text_print`, `text_print_int`, `text_print_fx`, `text_color`, `text_scale`, `text_wrap` |
| Primitives | `prim_arena`, `prim_mode`, `prim_box`, `prim_obox`, `prim_quad`, `prim_flush` |
| Collision | `col_sphere_sphere`, `col_sphere_aabb`, `col_aabb_aabb`, `col_point_aabb`, `col_ray_aabb`, `col_ray_tris`, `col_sphere_mesh`, `col_slide` |
| World helpers | `grid_*` voxel grids, `lvl_*` levels, `ctl_move` character controller, `act_*` actors, `prt_*` particles, `path_*` pathfinding, `cam_follow` rig |
| Controller | `pad_down(mask)`, `pad_pressed(mask)`, `pad_released(mask)`, `pad_stick_x()`, `pad_stick_y()` (each an `fx` from -1.0 to 1.0), `pad_present` |
| Save | `save_open(magic, version, words)`, `save_load`, `save_set(i, v)`, `save_get(i)`, `save_commit`, `save_clear` |
| Audio | `aud_play`, `aud_stop`, `aud_song(id)`, `aud_song_stop`, `aud_volume` |
| Random | `rand_seed`, `rand_u32`, `rand_range(lo, hi)`, `rand_fx` |

Buttons are `SG64_PAD_A`, `_B`, `_Z`, `_START`, `_DU`, `_DD`, `_DL`, `_DR`, `_L`, `_R`, `_CU`, `_CD`,
`_CL`, `_CR`; masks combine with `|`. They are never `KEY_*` here.

### Drawing order

1. `frame_begin`.
2. The camera, once.
3. Lights and fog.
4. The 3D: `mesh_draw`, `bill_draw`, `prim_*`.
5. The 2D layer last: `hud_*` and `text_*`. Rectangles are a layer after all the 3D.
6. `frame_end`.

The light only affects models drawn in a `LIT` mode, so do not leave the ambient term black. Render
modes are a closed set (`SG64_MODE_OPAQUE_TEX_LIT`, `_OPAQUE_SOLID_LIT`, `_CUTOUT_TEX_LIT`, `_XLU_TEX`
and others, nine in all). A model with no texture draws solid on its own.

### Drawing boxes without any model file

`prim_box` draws an axis-aligned box from integers, in a batch you flush once, and only the faces the
eye can see:

```c
u32 arena[2048 * 4];                       /* four words a vertex */
...
frame_begin(&dl, 0x203040FFu);
cam_look(eye, at);
prim_arena(&arena[0], 2048u);
prim_mode(SG64_MODE_OPAQUE_SOLID_LIT);
prim_box(cx, cy, cz, hx, hy, hz, 0.0fx, 0x8C8A7CFFu);  /* centre, half sizes, yaw in turns, colour */
prim_flush();
```

### Saving

```c
#define SAVE_MAGIC   0x4D594731u    /* four bytes of your choosing */
#define SAVE_VERSION 1u
#define SAVE_WORDS   8u

save_open(SAVE_MAGIC, SAVE_VERSION, SAVE_WORDS);
if (save_load()) { best = save_get(0); } else { best = 0u; }
...
save_set(0, best);
save_commit();                  /* on a real event, never every frame */
```

`save_load()` returns 0 for a fresh cartridge, a corrupted save, or a save from a different `version`,
so bumping `version` turns old saves cleanly into "no save".

## Assets are constants

| Kind | Constant | What you do with it |
|---|---|---|
| a 3D model | `MESH_duck` | `u32 h = mesh_load(MESH_duck);` then `mesh_draw(h, matrix)` |
| a picture | `TEX_skin` | `u32 t = tex_load(TEX_skin);` then `tex_bind(t)` |
| an animation | `CLIP_walk` | `u32 c = anim_load(CLIP_walk);` then `anim_play(mesh, c, seconds, loop)` |

Load in `main` before the frame loop and check the handle: `mesh_load` returns 0 when the asset is not
there, and drawing with a bad handle is a panic. At most 64 meshes, 63 textures and 32 clips are
loaded at once. A new SG64 game carries no assets.

Models are baked to a triangle budget (800 by default), with textures of 32x32 or 64x64 that fit the
4 KiB of texture memory, one live texture at a time.

## Budgets

| Wall | Total |
|---|---|
| game image (code, constants, globals) | 2,176 KiB on a 4 MiB machine, 6,272 KiB with the memory expansion |
| the slot in the cartridge, image and assets | 63.9 MiB |
| heap after the frame buffers | about 1,126 KiB for meshes, textures and clips |
| assets in one cartridge | 4,096 |
| save | 508 words, or 8,188 on the larger chip |

Big data belongs in the cartridge, not in RAM: store a table, a level or a script as an asset and read
it when needed. A 1 MiB `const` array costs 1 MiB of RAM for as long as the game runs.

## Panics

A game that breaks a rule stops on a panic screen with a code. `SG64_PANIC_GAME` (321) is the engine
refusing a call (a handle that is 0 or out of range). `SG64_PANIC_ASSERT` (320) is your own `assert`.
The app boots every cartridge it builds before handing it over, so a cartridge the runtime would
refuse arrives as a build failure with the reason in words.

## What a 2D profile programmer must unlearn

There are no sprites, no tile maps, no `spr_*`, `bg_*` or `snd_*` calls: a character is a mesh, a HUD
is `hud_*` and `text_*`, a scrolling backdrop is geometry with a texture, and sound is `aud_*`. Keys
are `SG64_PAD_*`. Angles are turns. `fx` is 16.16. There is no entity pool, platform library or
cutscene interpreter.
